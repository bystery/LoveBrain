## §0 总任务目标（所有评审与执行会话共同遵守）



**以 `D:/LoveBrain` 原始项目为公平参照，在同一模型服务下，删除、重写、合并并循环优化完整 harness，得到聊天更有效、记忆与上下文更干净、token 更省、等待更短、维护更简单的实现。**

API 是被固定下来的模型服务；harness 是被改进的参赛对象。二者的边界是：

**harness 组织输入、API 返回文本，返回的文本只当数据。**



训练对象包括 system 资产（core 等）、意图指导、HER/ME/补充信息处理、知识与记忆写读/检索/注入、上下文组织和预算、输出与调用策略。这里迭代机制和提示词，不训练模型权重。



- **原版是参照，不是必须继承的模板。** 基线对被比较范围忠实；候选可以大幅删减和重新设计，不默认旧资产、机制分层和复杂度都有价值。用户“80%–90% 没用”的判断通过删除/替换实验检验，不伪称已经测得该比例。

- **目标包含正向聊天能力。** 除准确与少污染，还要根据关系、有效意图和对方反馈，承接、主动开话题、留钩子、调侃/调情、推进见面或深入交流，并在合适时收尾；不能只训练成不犯错但平淡的接话器。

- **完整主线是：目标与量尺 → 连续故事和评审卡 → 公平参考与最小对照 → 提示/机制候选 → 真实对照与质量/资源评审 → 保留或淘汰 → 独立故事检验 → 原项目接入。** 数据、评审和候选应按需要共同推进，不能长期停留在搭考场或恢复原版。

- **有效效果迭代必须产生结果判决。** 候选准备、离线通过、打包和文档修订不能冒充效果改善；真实比较没有收益也应如实淘汰/保留不确定，而不是改指标或反复补跑到赢。

- **实验应允许简单方案胜出。** 除原版和改进候选，还应建设最小 harness 对照与重要组件的删除/替换实验，检验原版复杂度是否值得；质量相当而资源明显降低也是进步。

- **回复长度不另设优化目标（用户2026-10-24明确纠正）。** 提示词精简、资源或性能改善，不要求回答同时更短、更“利落”。回复长短按情境和用户需要判断；字数与输出token是观察值，不单独扣质量分、不作为晋级前置。质量相当而总资源或性能有实质收益即可支持效率型候选，不能额外强求聊天质量也必须提高；仅有重复、偏题或破坏真实互动等具体证据时，才判相应质量问题。

- **完整性能与花费口径（用户2026-10-25强调）。** 不把总token下降等同于性能全面改善。每个真实候选同时评质量/事实与污染、原始协议与实际消费成功率、用户可用回复的端到端等待、p50/p95/超时、实际API usage与可核实费用、维护负担。首个内容到达不等于首选已可发送；没有分段证据不猜排队/推理/传输成因。性能与费用是主线，不长期只优化某一段prompt。

- **先把质量评估基准做实（用户2026-10-25最新方向校正）。** 当前语义/互动评审仍含未校准AI主观判断，不能因程序完备、评审卡存在或本会话叫独立复核，就视为裁判可靠。当前下一主工作包先对齐总流程、任务分布、事实与自由表达判据、用户风格锚点、裁判标定及按故事划分；修错卡和校准应得到足够资源，不以“别搭考场/省时间”回避。未开始的192次扩量性能任务暂不作为第一优先，既有成果保留、持续授权不撤销。明确标准后冻结并复用，不要求每轮重建评估机，也不无限调judge到赢。对齐草案：`refs/experiment_protocol_20261023/EVALUATION_MASTER_DRAFT_20261025.md`。

## §0.1 全局推进纪律（用户直接指令）



**每次向 worker 下任务或独立复核其交付，必须以总目标和当前里程碑为基准，合并安排足量的高价值工作，并实际推动整体进度。不能让临时小问题取代主任务，不能一轮只修一个冷僻边角、下一轮再补另一个边角。**



1. **从里程碑倒排任务，不从新发现的漏洞列表决定全部工作。** 每轮说明当前阶段、尚缺的关键产物、这一批推进哪个主里程碑；优先真实对照、有效候选、代表性数据与可用评价，而非扩大自检数量。

2. **任务量按完整交付组织。** 能在授权和依赖范围内连续完成的接线、候选实现、必要反例、调用清单、实跑、全量初审、配对报告与下一假设合并推进，不人为拆成多轮等“继续”。任务多寡以能产生完整结果为准，不以堆无关任务或多造文件为准。

3. **只把真实阻断主线的问题作为前置。** 影响当前比较正确性、常见用户体验、核心信息边界、调用预算或证据真实性的问题合并处理；不影响本批有效结论的低频边角、纯文案、非使用范围功能进入 backlog，不能无限抬高开测门槛。判断必须给出对主任务的实际影响，不能只凭“低频”放过实质破坏。

4. **修故障族，避免逐例缝补。** 同类问题用通用规则与代表性正反例一次处理；不要围绕题号、车次、地名、杯子等已知素材特化。允许为一个清晰设计假设合并改多个文件，不把“一个主变量”误解为一次只能改一行。

5. **签收已有成果，控制复核范围。** 已验证且未变化的部分不重复退修；发现新证据才重开相关项。独立复核既给准入判决，也给下一批完整主线任务；不能只不断找小洞而不推动进入真实实验和候选选择。

6. **基础设施达到本批需要即可进入实验。** 不要求每轮重验全平台、移植全部安卓能力、搭系统隔离、扩完几百题或校准完所有 judge。检查覆盖实际改动与真实风险，确定性测试/捕获不代替真实模型效果。

7. **不把用户当人工调度器。** 有既有授权就连续执行，不重复申请同一许可；缺真实调用额度时只合并提出一次明确清单，同时继续有价值的离线候选、公开扩题与评审准备。不得复活关闭额度或擅自补跑；独立题缺件不阻塞公开开发诊断。

8. **先报用户价值，再报工程检查。** 每轮第一屏给出：总阶段、本批实际推进、真实比较是否发生、质量与代价结果、保留/淘汰判断、下一批主线任务。自检数、波次数、文件数、打包数和“全部 FIXED”不能代替总进度。

9. **临时请求不取消总任务。** 回答临时问题后仍保持主线、已接受决定和当前实验边界；除非用户明确改变目标，不随局部反馈重新发明考场或切换研究目标。

10. **禁止用扩大工作量掩盖没有进展。** 连续交付只有离线修补而没有进入可执行实验时，必须解释阻塞的实质影响、给最短替代路径，并转入下一个有价值产物，不能继续循环“已准备好、等下一波”。



下一阶段完整任务书：`D:/lovebrain-arena/refs/experiment_protocol_20261023/HARNESS_OPTIMIZATION_EXECUTION_GUIDE_20261024.md`。它提供执行路线；当前阶段和结果以真实批次证据更新，不把旧状态描述当成永久任务。



## §1 角色与循环本体



Worker = "Harness 进化工程师"，负责连续执行合并工作包。独立复核会话负责检查整批证据、判决与推进下一阶段。**一轮 = 一个有明确假设和结果判决的实验批次，同一会话可以连续完成多轮，不要求新开窗口。** 未做真实比较时如实称候选准备/工程修复。

**不存在、也不允许存在任何循环驱动/自进化脚本。** v1 假循环的教训（脚本伪造被测产物再自断言）是本场存在的理由。确定性搬运工具（iso_run.py / api_trial.py / lb_scorer.py / aggregate）允许；变异、归因、晋级判断由 Worker 本人完成。



## §2 被测对象：harness 的机制组合



参赛 harness = 一个候选目录（`candidates/<name>/`），包含：

- `mechanism/`（**核心训练对象**：记忆怎么存、怎么取、意图怎么处理、上下文怎么组织；

  实现与 `arena/lb_assembly.py` 相同的装配接口，可自主决定内部结构）

- `assets/system_prompt/*.md`（提示词资产，属 harness 的一部分，**可以改**）

- `params.json`（装配参数；可选 `output_contract`；输出用途与数量按该批预登记，改数量须报告功能/选择负担/成本交易，不强迫凑八句；不在运行中改合同）

- `MECHANISM.md`（必填：存储/检索/意图/上下文四决策各一段）

- `IDENTITY.md`（≤15 行：本代假设＋机制 DNA＋父本）



**API 的角色**：`http://127.0.0.1:17770/v1`，model `dsf`，温度 0.7。

同批比较时端点/model/采样固定；**换模型 = 换考题条件，不是 harness 进步**。

harness 把组织好的 system/user 发给 API——不是把 Python 源码发给 API 执行。



**被观察的**是"该 harness 在这套题上的真实回复与后续行为"，**被改进的**是 harness 机制。

`reference_product_v1` = 按声明范围移植原版 LoveBrain 的**参考基线**；保真证据和未覆盖能力单列，不仅凭名称宣布完整生产等价。最小对照与候选另建身份，不改弱参考基线来制造优势。



### §2.1 变异分类（改的是 harness，版本化）



| 类 | 变异层 | 例 |

|---|---|---|

| M1 | 记忆存储结构 | markdown → 结构化事实条目（含来源/时效/置信度） |

| M2 | 记忆检索与注入 | N=2 → 完整交流单元 + 活跃状态 + 检索召回 |

| M3 | 意图处理 | 意图显式路由：不同意图（调情/邀约/安抚/收尾）走不同装配分支 |

| M4 | 上下文组织 | 对话分区、压缩摘要、关键约束前置（防 Lost-in-the-Middle） |

| M5 | prompt 资产设计 | 删除冗余 core、压缩规则、重写任务与风格；本身可以是主要实验变量 |



- **取消按 M1–M5 类别强制配额。** 不为满足“必须改机制”而额外加代码；prompt 删减也可凭真实质量与资源证据保留。持续检查是否覆盖整体目标，不把长期只调措辞当完整架构优化。

- 一版 harness 应有可检验的主要设计假设；允许合并修改同族逻辑或建设整体新架构，按证据区分整体收益与具体组件贡献，不凭空宣布每个改动都有独立作用。

- 改 harness 只产生新 harness 版本，**不重建考场、不重验整座平台**（见 §9 版本分离）。



## §3 考场与评分（确定性铁律）



- 考场运行时：`arena/lb_runner.py`（装配 → 适配器 → 落盘 → 评分 → manifest）；机制层变更通过候选的 mechanism/ 接管装配，基线对拍豁免权仅属于 round_0_baseline。

- 装配器 `arena/lb_assembly.py` 与 Kotlin 原版的对拍基准是字节一致；任何对**基线装配**的改动必须先过对拍（机制变异不受此限，但必须在 MECHANISM.md 说明差异点）。

- 唯一计分器：`arena/lb_scorer.py`（rubric 层 1）。judge 评审团（层 2）永不单独触发 veto。

- 评分协议权威文本：`benchmark/rubric.md`。

- 成本记实际 API usage、全部调用/失败与时延；评审和研发成本另列。有可核对单价才报金额，未知不填零；字符或估计 token 不冒充真实 usage。质量与资源共同参与选择，见 §5。



## §3.1 开源参照义务（定期）



**每 3 轮、以及每次冠军替换前**，Worker 必须做一次开源机制扫描（Letta/MemGPT、mem0、A-MEM、GEPA、LongMemEval、LoCoMo、主流 RAG/记忆架构等），写 `logs/round_N_scan.md`：列出 ≥3 个可借鉴机制，明确"引入 / 否决 + 理由"。闭门造车轮次作废。



## §4 题库纪律



- 题库建设目标 = 约 200 请求位的连续剧情及用户风格锚点；开发/选择/最终集按故事与模板族划分。**建设目标不等于已完成数量**，现成材料、运行覆盖、独立性和暴露状态按实际清单报告；不等待全题库完成才做公开开发实验。

- 题目模拟真实用户输入三通道：聊天记录 + 补充信息（note）+ **意图（intent，部分题有）**；gold 挂意图契约（rubric §2 C10）。

- **封板后改题 = 舞弊**。封板前（pilot 窗口）是唯一的题目迭代期。

- 同一故事的改写必须留在同一数据划分；B 线只对最终候选开一次。

- 题目 schema 与探针矩阵：见《题库设计_200轮剧情线》。

- **B 线封存（v1.3 Phase 0 强化）**：`benchmark/b_line/` 为物理封存目录。开发迭代、机制变异、

  调参、自动化巡检**一律禁止读取其内容**；仅最终验收（争冠盲评）运行一次，运行后不得按逐题

  错误修补。违反即当轮变异作废。

- **Phase 0 事件边界（v1.3 新增，配合 runner v2 消毒边界）**：候选可见输入 = 真实 HER/ME 消息 +

  IDEA 备注 + 意图 + 时间戳，永不包含 gold / 测试替身台本 / 未来轮次；候选输出永不写入后续轮

  已发送消息；候选经 lb_gateway 调模型，每次调用强制记账（calls.json 落盘可复核）。



## §5 晋级（约束优化，质量主导）



- **质量、污染、成本、时延与可维护性共同决定保留。** 程序层只判它能确定的合同与边界，不是聊天质量或晋级的唯一依据；具体收益指标与退化保护在该批运行前固定。

- 质量改善且严重错误/污染与资源无实质退化，可以保留；质量在预定可接受差异内相当而资源明显降低，也可以保留。质量换资源的交易显式报告，不由 worker 代用户接受。均分微升不能覆盖严重退化。

- 每批报告配对胜/平/负/双方失败/不确定、故事级结果、首选与备选覆盖和真实资源。未校准 judge 不独自判冠军；公开开发改善、独立泛化、用户愿发与完整原版优势分别证明。未知不当通过，没有实际优势不替换父本。

- 五步晋级流程 + 第 6 步人工对齐检查点（HITL，降频为攒故障族收官再报），见 rubric §7；已知故障回归（refs/KNOWN_FAILURES.md）是硬门。

- 报告不确定性；请求位嵌套于故事，不能当相互独立样本。只有满足所用统计方法假设时才报相应上界，不能套用 N=请求位数来夸大把握。



## §6 权限与信任边界（本模式口径）



- **harness 代码由本项目编写**（Worker 是可信作者），不是恶意第三方提交物：

  Worker 审核自己的改动并本地执行，是普通开发行为。因此**不把 OS 账户/防火墙/

  主仓 ACL 隔离当作试考前置**；`tools/g08_deploy.py --apply` 已硬拒绝（撤回）。

  旧隔离矩阵的 FAIL 事实原样保留，不改写成 PASS，也不声称完成了抗恶意代码隔离。

- **API 返回物只当数据**：只经 `json.loads` 解析；不 eval/exec/import，不执行

  返回的代码/命令，不把返回里的路径当路径用，不自动补问修 JSON。

  出站请求体按白名单构造（无 tools/functions/tool_choice）。

  实现点 `arena/api_candidate.py`，验收点 `tools/test_api_boundary.py`。

- 评分器、rubric、题库、评分卡、账本只由可信侧改动；评分依据用**评估侧原题快照**，

  生成草稿不冒充用户已发出的历史。

- 不同候选使用隔离的记忆实例；同一故事按时间连续，换故事清空。

- 网页版 judge 通道遵守投喂合规：禁止向网页版粘 ground truth / 未脱敏隐私

  （只粘待评候选输出与脱敏上下文）。

## §8 停止条件



预算上限或真实证据/状态/配置异常按本批冻结条件停批；连续 3 批无实际优势时暂停或更换研究方向，不重试到赢。judge 分歧成为瓶颈时调整评审路径，当前故障族稳定解决时进入下一主线目标，而非继续围绕它缝补。局部停批/缺件不自动停止其他已授权且独立可做的主线工作。



## §9 版本分离（改一次 harness 不等于重建考场）



每份结果绑定四类身份：考场/评分版本、harness 代码＋资产版本、题目/卡版本、API 实际配置。



- 改 harness 提示词或检索/记忆代码 → 只产生新 harness 版本；同批考场、评分、题目不变。

- 修评分器 → 单独版本化，旧答卷优先离线重评，不重烧模型。

- 修题 → 新题版本，保留旧原件；历史答卷展示当时实际输入。

- 改报告文字/证据路径 → 只是报告，不构成新调用许可，也不假装绑定了从未运行过的代码。

- 打包、建管理员账户、跑完整旧隔离矩阵，**都不是**每轮训练的例行步骤。



## §10 评分自由度（继承，不重做）



- 参考答案规定事实、意图、状态与必要边界，**不规定唯一措辞**：允许自然确认、

  新提议、玩笑、调情、合理旧事回扣、合适的短回复与合法不回。

- 不逐字匹配、不强迫命中参考关键词；也**不允许**与事实矛盾的漂亮话过关。

- 分层记录：程序合同 / 事实语义 / 互动质量 / 用户愿发偏好。程序 10 分 ≠ 愿发。

- 合法 no_reply 与普通回复分开审查；要求回答的轮次不能靠全不回来拿高分。
