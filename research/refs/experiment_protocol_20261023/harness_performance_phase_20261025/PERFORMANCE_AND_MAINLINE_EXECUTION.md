## 2. 性能究竟怎么测：四张表一起看

### 2.1 效果与可靠性表

- 首选内容的任务完成/事实/主体/日期/状态/隐私与上下文污染；备选另审，不能一个好备选掩盖坏首选。
- 目标是否实际引导承接、钩子、调情、商量、深聊；目标关闭/反馈变化是否跟随；允许多种表达，不用关键词或问号数量代替效果。
- **传输成功率、原始模型协议通过率、harness消费后协议通过率、语义可用率分列。** 不能把HTTP200当业务成功，也不能把一个键名错写自动当正文完全不可用。
- no_reply整轮动作与directions里的null分开。v5旧批真实计数是方向null原版7/v5 12，整轮no_reply双方0，旧报告“null一次没用”须更正。
- 未评或语气存疑记未知，不记通过；用户愿发票由用户给，不由worker以“原样可发”代投。

### 2.2 等待性能表（单调时钟记录，不靠秒级日志相减）

| 时间点/指标 | 含义 | 不能混淆的口径 |
|---|---|---|
| turn_start→request_start | 取状态、装配、序列化、必要IPC等 | 单独列冷启动，不能只计HTTP漏掉harness开销 |
| request_start→headers | 收到HTTP头 | 不是首token，也不是纯模型排队 |
| request_start→first_content | 首个非空文本delta到达，TTFT的客户端近似 | 不把role空delta、心跳、响应头当首内容 |
| turn_start→first_preview | 能展示一个完整首选文本的预览 | 不完整JSON预览不是已经通过消费验证的可发送答卷 |
| turn_start→first_usable | 当前约定的消费/协议校验通过后，首个选项真的可用 | 用户点生成到可复制是核心体验指标；若实际必须等完整JSON，就如实记等到完整 |
| request_start→last_content→terminal | 最后内容、结束帧、usage收齐各自时刻 | 末尾结算等待不能混作继续产出文本，也不能为了快显示丢账 |
| turn_start→all_ready | 全部可发选项解析、规范化、可展示 | 这是完整答卷端到端耗时，不等于TTFT |
| persisted | 必要状态与审计完成 | 若用户可显示与持久化解耦，要记录两者，不掩盖失败 |

报告p50/p90/p95/max、每故事、重复间差异、超时/失败率、总批次墙钟。超时不从分母删除；失败与超时分列，并报告成功样本分位数的条件性。默认沿用120秒调用超时，若因实际服务要求调整，在运行前两臂同设并登记，不能看到慢样本后延长或剔除。

从客户端TTFT不能进一步拆出纯排队、prefill、服务代理与网络各用了多少；没有服务端trace就写不可分辨。解码tokens/s只有确实测到有效内容产生区间且分母有意义时才报；单token探针不算解码吞吐。

若实际增加流式显示，原版和新候选在性能对照中使用同一公共传输/计时条件；原版Android本已有generateStream，不能把过去移植中仅用非流式的劣势包装成候选独有收益。公共改造与候选改进分开登记。
