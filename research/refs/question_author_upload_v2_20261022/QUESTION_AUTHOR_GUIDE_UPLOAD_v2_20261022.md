# LoveBrain 出题指导书 · 上传自包含版 v2

日期：2026-10-22。适用对象：只能读取本会话上传附件、不能访问本地项目的专门出题会话。

**使用约定：本文件本身就是完整工作说明。无需读取电脑目录、旧会话、项目 zip、源码、网页或其他文档。文件名仅用于交付命名，不是要求你读取本地文件。** 不假定你知道任何历史争论。没有附件的图片、代码和资料视为不可用，不能假装已经看过。

本文件是出题委托的规范；不是考场已验收完成的声明，也不是调用考生 API、修改系统或训练考生的授权。用户在聊天中给的新要求优先。

## 1. 产品是什么，题目到底考什么

LoveBrain 是聊天旁边的回复助手：用户把收到的话、自己已经说过的话、给助手的私密备注和当前意图交给它，助手提供几条可选回复，用户自己决定改不改、发不发。**它不自动代聊、不自动发送。**

“考生”是 harness，即组织模型的机制、提示资产和参数：怎么记住事情、怎么检索、怎么处理意图、怎么组织上下文。迭代这些机制不等于训练模型权重。

考场应判断：回复是否事实与主体正确、合乎当前关系与动机、自然且值得接话；需要时是否记得旧事、不需要时是否不打扰；后续真实请求中的行为是否正确。内部知识库记录仅用于解释原因，不能代替最终回复表现。

优先级：明确事实与边界 > 本轮有效意图 > 当前情境 > 持续意图 > 关系阶段默认倾向。质量优先；费用如实记账，用户授权的调用上限必须遵守。程序分满分不等于真人愿意发送。现阶段自动 Judge 不能单独决定淘汰、晋级或通过。

## 2. 本次直接开工的范围

**首批交付：3 条不同生活故事，每条约 8 个请求位，共约 24 位，全部作为公开开发题。** 关系分别覆盖普通朋友、新认识投缘、逐渐暧昧；至少三个生活领域。先完成整批，不每写完一个字段就等用户口令。

先写生活轨迹，再写连续台词，再登记观察点与评审条件，最后给 JSON 草案和自审。首批交付后只安排一次约 6 段的个人语气标定。用户不负责找格式、时间和代码问题。

后续题库的建议规模为：开发 80 位、独立选择 40 位、最终封存 B 80 位，共约 200 位。首批 24 位可以算进开发 80。该数字是初版设计目标，不是凑数指标，更不表示必须先写几千道才可试用。完成首批后，按用户反馈统一扩充；不提前把未交付的后续题算“已完成”。

已有工程项目有开发题和机械压力题；无需、也不允许为了本任务读取它们的内容。你从这里的公共规范出发独立写新故事。只由用户另外批准且实际上传的脱敏素材才可参考；不能把虚构台词说成用户真实聊天。

## 3. 三种计数，三种资料边界

聊天消息是一条 HER/ME 发言；请求位是用户请助手生成一次回复的节点，一位可包含多条消息；模型尝试是 harness 实际调用一次模型，多阶段和失败都算。200 请求位不等于200单句，也不等于每轮训练必须花200次调用。

| 内容 | 助手/考生能否看到 | 是否已经对聊天对象说过 |
|---|---|---|
| HER | 能：对方已经发来的消息 | 是，对方说的 |
| ME | 能：用户已经发送的消息 | 是，用户说的 |
| IDEA / note | 能：仅给助手的私密备注、计划或猜测 | 否，不得冒充 HER/ME 原话 |
| 有效 intent | 能：用户希望怎么回复的自由文本意图 | 否，是给助手的目标 |
| persona / initial_kb | 只包含明确允许已知的背景 | 不等于本轮聊天原句 |
| gold、作者解释、完整未来剧情、探针名称 | 不能，只给评估侧 | 不能泄漏到任何可见字段 |

备注可包含用户补充的信息，但“她可能在试探我”只是猜测，“我想回……”只是草稿。不得据此断言对方动机或已经发送。候选生成的推荐、方向句从来不自动变成后续 ME 历史。

## 4. 可交付的题面数据格式

每条故事一个 episode JSON 对象。允许用文件交付；若界面不能创建附件，用带文件名的完整 JSON 代码块交付，供本地工程人员确定性导入。不得要求本会话运行项目验证器。

| 字段 | 类型和含义 |
|---|---|
| episode_id | 唯一字符串；正式题使用中性编号，例如 E001，避免编号泄漏考点 |
| persona | 对象；允许已知的双方画像、关系/地点/表达习惯，未知项不要编造为事实 |
| initial_kb | 对象；只允许开局预置的真实背景；自主记忆故事设空对象，不把后测答案预置进去 |
| turns | 按请求发生时间排列的数组 |
| turns[].case_id | 唯一字符串，如 E001_T01；以 episode_id:case_id 作为全局身份 |
| turns[].turn_type | 首批统一用 reply；本任务只做收到对方消息后的主链路，不扩到草稿润色/谈心引擎 |
| turns[].input.messages | 数组，每项 role 为 HER 或 ME，text 为字符串，ts 为时间字符串；不能放作者说明或角色 IDEA |
| turns[].input.clock | 请求发生时间，统一用 YYYY-MM-DD HH:MM，Asia/Shanghai |
| turns[].input.note | 可选字符串，承载 IDEA 私密备注；不是演员台词，也不能藏评分标准 |
| turns[].input.intent | 可选对象，建议 {"enabled":true,"text":"自然承接，不急着邀约","status":"ACTIVE"}；关闭设 enabled=false；自由文本，不是固定任务标签 |
| turns[].input.may_decline | 布尔，true=本轮允许选择不回；不等于必须不回；没有则按 false |
| turns[].input.kb | 可选对象；只有明确公开的当前知识输入才用，不把未来事实/评审材料塞进去 |
| turns[].gold | 对象，属于评估侧；开放式聊天默认空对象，详细语义判据放单独评审卡 |

每次主链路请求的最后一条真实消息必须是 HER；ME 只能作为已经发送的背景。时间戳用同一格式，请求 clock 不早于任一可见消息，跨请求时钟不倒退。注明长时间间隔，但不能靠时间跳跃制造“模型见过”的假历史。

messages 中先按时间呈现真实 HER/ME；对方连发几条时，应作为同一待回复语境理解，不能只看最后几个字。source_ids 的 m0、m1…由本次请求中的真实 HER/ME 顺序编号，每次请求重新起号；私密 note 不占号。

工程资料还可有作者台账、划分标识和观察标签，但它们存单独清单/评审卡，不能因此要求修改考生输入契约。本会话只提交这些明确定义的字段；不知道的运行细节记“待本地适配核验”，不能编造。

## 6. 考生输出契约：出题者需要知道的部分

默认正常输出为单一 JSON，包含 response、directions、analysis。response 默认推荐/清醒有锋芒/俏皮/温暖四种风格；directions 默认四个可直接发送的候选槽位，不是给用户看的“你应该怎样回复”分析。**8个槽位不等于强制8条非空句子，合法 null 不应被误杀或被迫凑话。** 实际候选可声明不少于8槽的扩展契约，工程人员处理版本对照，出题者不擅改契约。

一个结构示例：

```json
{
  "response": {
    "recommended": "歇会儿吧，回头聊",
    "bad_boy": null,
    "playful": null,
    "warm": null
  },
  "directions": [
    null,
    null,
    null,
    null
  ],
  "analysis": {
    "topic_status": "same",
    "topic_label": "搬住处",
    "scene_facts": [
      {
        "text": "她说已经搬完",
        "source_ids": [
          "m0"
        ]
      }
    ],
    "ongoing": []
  }
}
```

这只是格式示例，不是你要让考生背的答案。首选、备选分别审：首选正确不代表备选允许编造；备选有一个关键词也不代表首选记得事实。

- analysis.scene_facts 为事实数组，text 是字符串，source_ids 指向本轮真实消息；编号存在不等于语义支持，要核对事实主体和出处。
- analysis.ongoing 为事项变更数组；topic_status 一般为 same/drift/new。不要靠题库强迫某个内部存储格式证明聪明，应看下一轮实际行为。
- 合法不回可使用 {"action":"no_reply","reason":"对方明确收尾，无需再发"}，也有兼容旧式 decline 形式。本轮许可与候选的共同输出能力需要本地工程适配核验。
- no_reply 不能同时夹带待发正文；允许不回时，简短自然收尾也可能合格。必须回复时，不能用沉默回避所有问题。
- 回复草稿里的未来建议、观点和调侃不是“已发生事实”；不因没有事实出处就禁止合理提议，也不能把提议写回成已约定。

## 7. 12个能力族：正向与反向保护一起设计

| 能力族 | 要观察 | 防止“过度保守也得高分”的反向保护 |
|---|---|---|
| 主体和来源 | HER/ME/note 分清、私密信息不泄漏 | 已有根据的 ME 经历可以说，不因有“我”就判编造 |
| 自由意图 | 理解有效意图、允许改变和撤销 | 意图关闭后不能继续强行推进；无意图不是无事可说 |
| 关系与语气 | 普通朋友/投缘/暧昧的分寸与互动 | 不把调情全部判违规，不把普通朋友直接当情侣 |
| 相关记忆 | 需要的早先信息影响现在的判断 | 无需显式复述记忆，行为正确即可 |
| 无关记忆 | 不被旧话题打断当前聊天 | 真相关的旧事不能一刀切屏蔽 |
| 更正与错人 | 同主体、同属性的新旧值有方向 | 历史引用、另一个人同编号不应被误删 |
| 事项状态 | 分清提议、确认、完成、取消 | 邀请不是同意；否定句里的“可以/一起”不是接受 |
| 时间地点 | 相对时间、异地、跨日正确 | 消息时刻不是活动钟点；合法的新邀约不能全禁 |
| 具体事实 | 有根据的时间/数量/编号不丢 | 未知可不确定，已知不能全删或每次反问 |
| 媒体 | 真实图片进入请求并正确使用 | 不可见时不装看过；文字描述不算视觉测试 |
| 冷场与收尾 | 允许低信息量、不回、转话题与重开 | 不能一见“晚安”就忽略后来重开的新问题 |
| 合同与后续 | 输出有效、失败留证、后续状态正确 | 不靠空输出、假记忆、补跑或编制分数过关 |

不是每条故事都塞满12族；在整批建立明确覆盖和正反机会，真实复用节点要注明，不虚增独立样本。首批缺某项（如图片附件）应如实记缺口，而不是用标签声称已覆盖。

## 8. 自然故事怎么写

每条故事先给一页“人物与生活卡”：双方关系、各自生活安排、彼此实际知道什么、未知什么、最近为何联系、说话长短和习惯、日期地点。先成立生活轨迹，再嵌事件。涉及亲密与暧昧的角色设为成年人，写实际分寸，不用单一强度代替不同关系。

至少跨工作/学习、兴趣、朋友、购物/居住、出行等三个生活领域。可以使用具体名词；禁止的是把题库内容反向写成考生规则。“交通题不能出现车票”同样是误解。

人物说话是因为有事想分享、有情绪、有空搭话、想试探、真有疑问，或单纯接梗。不要为了考记忆突然报一串信息，也不要让 HER 永远配合推进。允许不热情、冷场、少信息、没有结论，不把“哈哈/笑死/嗯”一律当无效题。

ME 必须有可核对的已发送历史，或明确没有：不擅自给用户补学校、加班、晚饭、个人习惯和已作出的承诺。用户只给一个模糊目标时，考生可以合理提问/试探，不用捏造经历填满回复。

调侃、暧昧、温暖不靠违禁词表或“越短越真人”判定。是否自然要连续读上下文、人物与动机。不能把某一句标准话术写进 gold 让所有候选复读。

## 9. 长期记忆与下一轮证据

分开命名四种能力：预置知识使用；空状态自主存储；窗口退出后的相关回忆；重启恢复。不要混成一个“长期记忆PASS”。

每个长期记忆观察位要给出：事实首次进入哪一次实际请求、中间经历什么其他话题、目标如何退出后测可见窗口、后测真正需要它做什么，以及无关轮为什么不应回提。不能把答案放 initial_kb、同义提示或题号里再证明候选记得。

一天/数周的日历跨度与消息/干扰长度分别记录。几天过去但事实仍在本轮输入，不算记忆召回；未交给考生的信息不能算它见过。首批至少设计一条完整的“见过—干扰—不在窗口—相关后测—无关后测”线，不宣称少量请求足以证明长期可靠。

固定 HER/ME 回放用来公平比较，不让考生输出改写后续剧本。所谓“下一轮”必须指实际安排了后续请求，不是作者给自己写一句预计会正确。没有后测的节点明确标无后测。

## 10. 评审卡与评分原则

每个请求位交一张隐藏评审卡：证据、允许的行为范围、明确失败、反向保护、下一轮观测和未解决歧义。评分侧可读，不能进入考生的 persona、note、intent 或消息。

示例：

```json
{
  "episode_id": "PUBLIC_FORMAT_EXAMPLE",
  "case_id": "PUBLIC_FORMAT_EXAMPLE_T03",
  "split": "dev_exposed",
  "families": [
    "状态更新",
    "收尾与不回"
  ],
  "evidence": [
    {
      "case_id": "PUBLIC_FORMAT_EXAMPLE_T03",
      "message_index_zero_based": 0,
      "role": "HER",
      "text": "总算搬完了，躺地上不想动"
    }
  ],
  "allowed_behaviors": [
    "简短自然收尾",
    "在共同契约支持时选择不回"
  ],
  "failure_conditions": [
    "仍把搬住处描述为尚未发生的约定",
    "臆造用户已经约好到场帮忙",
    "在明确收尾后强行新邀约"
  ],
  "required_reply_phrase": null,
  "contrast_design": "另一独立开发节点应覆盖收尾后被新问题重开，不能继续一律不回",
  "next_behavior_check": "本示例仅三轮展示格式，尚未提供下一轮状态验证，不宣称该项已验收",
  "review_status": "illustrative_only_not_user_rated"
}
```

语义评审关注事实/来源、主体、互动动机、时间地点、分寸、no_reply合适性、是否值得继续聊。个人语气偏好单列。

客观格式、非法编号、结构等交程序；有歧义的自然回复交人工监督评审。开放聊天的 gold 默认空对象；确需硬事实约束，指出事实与上下文理由，不自行发明评分字段/权重。不要以“必须出现这个词”代替是否正确承接，也不能把“未知”简单判成信息不足而放过明确编造。

你写的“像真人/可发”只能标命题方自审；没有用户亲自判过，不能写“用户愿发”。没有运行模型，不能出模型分数、胜率或故障清零结论。

## 11. 媒体与外部素材

本任务没有自动提供本地图片。若用户未上传图片，你可以设计媒体观察计划，但将对应素材标为 MEDIA_PENDING，先交其它完整文本题。不要写一个看似真实的本地路径、伪造图片内容，或用 caption 冒充模型已经读图。

有真实上传素材时，额外列素材标识、来源与许可、所需观察和不可见对照；由本地工程人员落文件、计算散列并登记。当前运行资料要求消息的 image 引用与可信 input.media.images 登记双向一致。media 登记属于工程校验数据，不应含评分提示。候选只应得到允许的图片。

同一照片、聊天素材及其派生故事属于同一素材家族，不跨开发/选择/B。无需联网找用户聊天、下载别人的私密内容或购买素材。

## 12. 数据划分与保密：出题会话能做到什么

建议初版开发80/选择40/B80，按完整 story_family 先划分，不按单题随机切。更名、换编号、换城市、同一事件骨架的派生版本都留在一个划分。首批公开24位及本文件示例只能留开发。

独立性来自角色不参与调参、内容未用于挑选修改、候选先冻结、访问与暴露记录可审计；不要求不同付费账号，也不因开了新窗口就自动独立。

**当前会话可以命题、检查、交付文件，不能替本地系统设置权限或证明硬盘已封存。** 如果用户把选择/B 全文上传给开发 worker，该内容已经暴露。对保管者交全文，对开发者只交不泄题的规模、覆盖、版本、散列与状态。摘要也不能透露具体谜底、剧情和逐题失败答案。

不得虚构独立出题人、管理员密钥、加密部署或哈希校验成功。无法取得可信保管条件时标“内容草案已完成/未技术封存”，不宣布 SEALED_READY。也不要因此停下公开开发 pilot。

选择集反馈用于改候选后，对后续版本不再是未见独立验证；留存暴露事实并另建新故事确认。B 最终一次，不反复刷题。

## 14. 本地工程人员的接口与禁止事项

出题会话交内容与格式草案；本地 worker 负责机械导入、字段/时间/媒体校验、散列、候选可见边界和可信保管。机械错误可以修，但台词/事件/语义判据变更要留版本，不能为了让考生成绩好而偷改题。

本任务不要求读取电脑、不要求安装东西、不要求创建子代理、不要求外部API。未提供的工具不假定存在。禁止自动调用考生、修改提示词以背题、修改评分器凑通过、购买额度或重跑旧实验。

本文件已经足够启动首批。不要让用户再提供完整项目、几十份历史报告或自己编题；真正缺失的个别素材记缺口并继续可独立完成的文本工作。
