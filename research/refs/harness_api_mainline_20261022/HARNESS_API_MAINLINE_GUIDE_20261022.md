# LoveBrain斗兽场：训练完整harness、对照原版的执行指导书

日期：2026-10-22。用途：交给本地worker，收回偏离用户目标的系统部署路线，完成首场24题开发试考，然后进入harness迭代。

## 0. 用户目标与本书优先级

用户最新明确的调用是：

```text
POST http://127.0.0.1:17770/v1/chat/completions
Content-Type: application/json

model = dsf
messages = [system消息, user消息]
```

**目标：训练出在代表性连续聊天题库上优于LoveBrain原内置harness的新harness。固定模型服务，把harness的意图、知识库、记忆、检索和上下文等机制作为改进变量，通过真实回复和后续行为检验收益。**

### 0.1 用户再次明确后的最终定义（本段优先）

- **斗兽场**＝连续故事题库＋参考判据/答案范围＋评测执行器＋评分和对照流程。
- **参赛对象**＝一个完整harness版本；实际被观察的是该harness调用固定API后的表现。dsf API是各参赛harness共用的模型服务，不能再把“只测试API端点”当成项目目标。
- **基线**＝用户原LoveBrain内置harness的真实实现/已验证等价版本。先取得原版同题分数及逐项表现，再与候选同场比较。不能偷偷替换成能力较弱的临时基线。
- **题库目标**＝几百个请求位组成的多条连续生活故事，配参考判据。首批24位只是启动开发评测的pilot，不是把总目标缩减为24道题，也不是用几百道互不相干的单句代替连续故事。
- **优化责任**＝在模型/参数、题面与评分口径固定且调用正常的有效答卷上，把质量缺陷作为harness待解决问题，不以“API不行”搪塞、不靠换强模型冒充harness进步。传输或评测工程事故单独记账，不当成回复质量。
- **胜出目标**＝整体优于原版，在已知错误上有改善且没有不可接受的退化；不只是格式10分或模仿某条参考句。最终用独立题检验泛化。
- **自由度评分**＝沿用既定的语义/互动评分边界；参考答案提供事实约束、可接受方向和反例，不是唯一标准措辞。无需推倒重做评分原则。

审查方上一轮“考生就是API”的概括不准确，现撤回。所谓不向API开放本地执行能力，只是调用方式；它不取消worker修改harness机制代码的任务，也不意味着冻结提示词或只调API参数。

本书落实这次用户纠偏，替代旧文件中相冲突的执行要求，特别是“必须部署系统账户才能试考”“所有提示词永久固定”“harness不得再改进”。不是新增账户、管理员、真实调用或清理授权。

此前审查方也有两处错误：把API模型与本地可执行代码候选混为一谈；随后又把整个harness说成必须固定，过度收缩了训练对象。本书同时纠正。**固定的是同批比较的考场和评分规则；需要改进的是harness。**

## 1. 谁在做什么

| 角色/对象 | 职责 | 可否修改 |
|---|---|---|
| 用户 | 定目标、语气偏好、调用总预算 | 用户决定 |
| 本地worker | 写工程、审查harness改动、组织实验和归因 | 可按本任务修改可信本地工程；不是被测API |
| 参赛harness | 提示词、知识库、记忆存取、意图处理、上下文组织、调用策略的完整组合 | 核心训练对象，可以版本化改进；不局限于改几个词 |
| dsf API模型服务 | 接收各harness组织好的messages，返回文本/JSON | 比较时固定端点、model和采样配置；不是替代harness的参赛对象 |
| 考场 | 选题、投影输入、调用记账、保存答案、评分、生成评审材料 | 同一比较批次固定；工程修复另行版本化 |
| 题库和评审卡 | 生活故事与评估依据 | DEV题可有版本；同批固定，卡留评估侧 |

“harness＋题目输入API”指**把harness组织出的指令和上下文发给API**。纯提示词harness可以直接成为system内容；包含检索/记忆逻辑的harness在本地先完成组织，再发文本。不是把Python源文件发给API让它在电脑上执行。

worker审核后执行自己开发的本地harness代码，是普通开发行为；不等于dsf API能自行改Python。不得直接执行API返回的代码或命令，也不自动导入API指定的路径。

这里的“循环训练”是反复改进harness并评估结果；普通chat/completions调用本身不会训练模型权重。

## 2. 唯一主链路

```text
已固定的题目＋该故事已见历史＋当前harness状态
  → 输入白名单（只有本轮允许材料）
  → harness组装 system / user
  → 校验实际请求配置与授权剩余额度
  → 先记attempt占额，再发HTTP请求
  → 保存真实请求、响应及原始答卷
  → 按输出契约解析和评分
  → 合格的记忆分析经通用写回规则更新harness状态
  → 按24张评审卡逐位做语义和质量初审
  → 合并故障族，形成下一版harness假设
```

首场请求体应与用户curl同一条API链路，示意如下：

```json
{
  "model": "dsf",
  "messages": [
    {"role": "system", "content": "由当前harness生成的完整系统提示词"},
    {"role": "user", "content": "本轮真实消息、私密备注、有效意图、时钟及允许注入的记忆"}
  ],
  "temperature": 0.7
}
```

这里的中文是字段说明，不是要原样发送的内容。temperature=0.7是沿用已有实验配置的首场方案，用户原curl没有显式写温度；执行前记录实际出站值，不能再发null然后猜测服务端默认。首场只用非流式文本，不增加工具接口。没有密钥要求就不强行制造密钥依赖；已有适配器若需兼容空认证头，统一在该适配器处理。

## 5. 输入、记忆和输出的必要规则

### 输入

- 发给API：当前允许的HER/ME真实消息、消息时间、当前时钟、persona、初始知识、私密note、有效intent、may_decline，以及harness从此前允许材料形成的记忆。
- 不发：gold、评分卡、卡内示例、未来turns、隐藏标记、运行脚本、评分规则答案、其他故事/候选状态。
- note不是已发送ME消息；推测不是事实；enabled=false的意图不是当前目标，也不是新禁令。
- 三故事分别初始化状态。同故事按时间连续；API不会替harness自动保存上一轮消息，历史/记忆必须由harness明确组织。
- 既有HER/ME回放来自题目，不能把生成草稿当成用户已经发出。固定HER后续反馈不能证明上一轮模型回复有效。

### 输出

- 答案只当数据处理，按既有文本/JSON契约读取；不eval/exec、不执行路径、命令或tool_calls。
- 当前回复契约、合法null和no_reply沿用已明确的公共协议。至少8个槽位不等于强迫8句非空；不改协议来美化某一版结果。
- 合法no_reply与普通回复分开审查；要求回答的轮次不能借全不回来拿高分。
- 类型合格不代表事实真实。analysis记忆写回保留来源、主体、时效与纠正规则；新事实不能由未来卡或gold灌入。
- 若API返回非JSON而本任务要求JSON：原文照存，记录格式失败，不把“能保存文本”写成“契约通过”，不自动再问一次修JSON。

## 6. 首场24题执行计划

首场目的：取得一份真实、可审查的基线答卷，定位harness问题。不是争冠，也不是证明长期记忆可靠。

| 项 | 固定方案 |
|---|---|
| API | http://127.0.0.1:17770/v1/chat/completions |
| model | dsf |
| harness | 已有reference_product_v1作为首场参考；本轮不同时换父本、提示词和模型 |
| 数据 | v0.2 E001/E002/E003，各8位，DEV_EXPOSED |
| 比较规则 | 首场先取得基线；后续父/子比较同输入、同模型配置、独立记忆 |
| 温度 | 首场方案0.7，实际出站明确落账 |
| 媒体 | 0，不能宣布视觉能力通过 |
| 生成预算 | 拟24 attempts，前提是离线确认每位仅1次生成；所有辅助调用同样占额 |
| 初始授权 | 本书未新增；旧8/52/66等授权不继承 |
| 自动重试 | 无。SDK/HTTP层也不得暗中重试 |

批准前把清单、执行/harness/题面版本和预算准备好，再一次提交用户。无有效预算时只做离线工作，不把用户贴curl理解成允许自动烧完整批。

首场只走一个固定harness，避免一开始就把调用翻倍。确认实际路径无辅助调用后，用户一句“按清单执行首场24次”即可批准该明确批次；不要逐题、逐故事索要许可。

### 失败策略与账本

- 跨3故事累计的授权级预算，换run/重启/改路径不能重置。一个故事结束不能提前关闭整个24次授权。
- 每次派发前持久占额；失败和未决也计消耗。无授权、超额、关闭、坏账、写账失败不派发。
- 传输失败、预算/账本异常：停批，保留已完成、失败和未运行位置，不自动补跑。
- 模型正常返回但格式/内容答错：登记为考试失败样本，不自动补问；可以按预定方案继续后续位置，并按既有规则跳过非法记忆写回。不是把所有坏答卷当网络事故。
- 失败发生在第k个位置时，只能报告真实已完成数量、该失败位和未运行位，不能承诺“任意失败都有23份成功答卷”。
- 记录实际attempt、请求体、响应原文/ID/model、时延、usage（缺失就缺失）、解析/评分错误。不要因报告更正重新发请求。

## 7. 评审：看答案，不只看程序分

自由度原则此前已明确，本节是继承与执行，不是重新立项。题目有参考答案不等于逐字匹配；事实、主体、有效意图、状态和必要边界必须满足，表达方式可以多样。保留自然确认、新提议、合理玩笑、调情、合适的短回复及合法不回。既不能“只因没有命中参考词就扣分”，也不能让与事实矛盾的漂亮话过关。

逐位读取对应卡，分别审首选、每个非空备选及analysis，不只抽查首选。

| 层 | 回答什么 | 不能替代什么 |
|---|---|---|
| 程序合同 | 格式、动作、字段、来源ID等是否合规 | 不能证明事实和人机感合格 |
| 语义事实 | HER/ME/想法、来源、纠正、时间地点、状态、有效意图是否正确 | 不用关键词出现替代语义 |
| 互动质量 | 动机是否接住、自然与否、分寸、是否值得继续聊、是否该不回 | 不靠安全冷淡或固定句式拿高分 |
| 用户口味 | 用户是否原样愿发/改后愿发/不想发 | worker或审查者不能冒充用户投票 |

已有三组自造正反对照能证明程序10分不等于语义正确；复用现有评审接线演练，不把抄写预期标签当运行。全量工程初审后，把需要个人口味裁决的材料攒成一批交用户，避免每条都打断。

允许新时间提议、自然确认、合理旧事回扣、新编玩笑和合适的调情。禁止的是编造既成事实、复活已纠正状态、泄露私密想法等具体错误，不是一串AI味禁词。

## 8. 训练循环与泛化

完整训练主线：**原版LoveBrain基线评测 → 归纳低分故障族 → 修改harness机制组合 → 同题、同评分、同模型比较 → 保留改善、检查退化 → 扩展连续故事并用独立题验收。**

reference_product_v1只有在既有保真证据支持时才代表原版；优先复用已经验证的原版与证据，不新造一个简化基线。所有后续候选同时与原版及当前父本比较，不能不断换父本就失去“是否超过原产品”的参照。

同批评分规则、参考判据、数据和模型配置必须一致；跨故事记忆实例独立，同故事连续处理。报告程序合同、语义错误、互动质量、愿发评价的分层变化与代表性答卷，不凭单个总分宣布超越。沿用既有评分和晋级口径，不为候选私改权重或新定一套更宽松标准。

```text
基线真实答卷
  → 按故障族归因
  → 提出一个可验证的harness改进假设
  → 变更记忆/检索/意图/上下文/表达中的一个主变量
  → 离线回归
  → 在已批准预算中做父/子同输入比较
  → 保留收益、登记退化，更新下一轮交接
```

- 记忆问题就改记忆，表达问题可改提示词；不强迫每轮只换词，也不为了机制配额无故改结构。
- 后续harness可以研究多阶段调用等机制，须计入全部真实attempt并在已批准范围内进行；首场每位一次生成只是基线计划，不是永久禁止机制调用编排。成本如实报告，质量仍是优化目标。
- 泛化规则针对主体、证据、事件属性、纠正方向、有效时间和互动状态。不得按E001等题号或车票、到站、杯子、番茄等本批词语写答案分支。
- 公开24题和同模板换名只算开发证据。新机制收益再用不同生活领域的成组正反例核验；不无限为单例打补丁。
- 不写自主变异/自动晋级驱动脚本。worker负责判断与改进，确定性批量执行和统计工具可以保留。
- 本循环改进的是harness，不更换dsf服务端模型权重；后者若要做是另一个明确任务。

## 9. 版本分开，避免改一次提示词就重建考场

每份结果绑定四类身份：考场/评分版本、harness代码＋资产版本、题目/卡版本、API实际配置。

- 改harness提示词或检索代码：产生新harness版本；同批考场、评分、题目不变。**不是换一个词就重新部署或重验整座考场。**
- 修评分器：单独版本化，已有答卷尽可能离线重评，不重烧模型。
- 修题：产生新题版本，保留旧原件；历史答卷展示当时实际输入。
