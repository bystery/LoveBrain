## 本轮核实与纠正

### 1. 旧事实未送达的方向成立，但报告引文不准确

直接读取 `E001/turn_06_E001_T06/calls.json` 的实际 user：

| 文本 | 次数 |
|---|---:|
| 刻字 | 0 |
| 杯底 | 1 |
| 留空 | 0 |
| 陶瓷 | 0 |
| 【进行中事项】 | 0 |

“杯底”来自本轮 HER 原话，不能据此说历史答案已提供；但也不能写“杯底出现0次”。准确结论是：当前问题在场，目标旧事实“留空、不刻字”未进入当时请求。

重放工具读取当前机制及当前 episode，而不是自动恢复旧执行版本，`prompt_sha_equal` 也未实现校验。因此应将其称为“固定旧输出的当前机制重放”，历史发生了什么优先引用原始 calls.json。不能由事后重放自动证明当时完整状态与当前一致。

“未注入记忆→导致判新话题→导致更多失忆”是有源码支撑的故障链假设；尚无控制实验证明每一箭头的因果强度。原版 selector 的局部逻辑有同类局限，不等于已在原版完整动态知识环境里复现同一失败。

### 2. v2 有可复现的污染风险，不能只看5项正向检查

检查 `candidates/v2_recall/mechanism/mechanism.py` 并直接调用其中函数：

- `is_recall_turn` 扫描整个 HER/ME 窗口。旧句“之前那件事已经结束了”＋最新句“今天午饭吃什么”，仍返回 True。旧回忆词会激活当前无关轮。
- `RecallSelector` 并非文档所说仅加 ACTIVE 项，而是追加所有未标 FINISHED/CANCELLED 的项目。构造30条无关 DORMANT 项，当前回忆请求下30条全部加入，未见相关性或数量预算限制。
- `MAX_RECALL_CHARS=1200` 只限制归档回忆段，不限制这批新增 ongoing 项。不能将1200字说成整个新增上下文上限。
- `restore()` 直接返回 `base.restore()`，未重装 RecallSelector；恢复后回忆型 ongoing 旁路可能消失，应补恢复前后行为一致的离线检查。

这些风险正对用户提出的“改善一点但污染和token增加”，应同批处理，不留到又一次付费试考后才发现。

### 3. 三处移植修复值得做，9/9不能代替完整保真

归档正文、路径读写和轮内ID冲突，属于修正适配器错误，不算候选创新。

上轮公平性检查指出的 `PromptBudget.byBlocks` 未接主请求、知识段读取 corrections 后未完成逐项过滤、主体解析与后台触发的范围差异，在当前代码/说明中仍没有整体收口。先对照 `refs/fair_baseline_20261023/FAIR_BASELINE_AND_REFACTOR_GUIDE.md` 逐项核销，不能仅以新增 t8/t9 推定全面公平。

前台开发诊断可以继续；完整“超过原版”的结论须等待相关能力进入公平比较范围。后台功能不涉及的短试考，明确标注即可，不要求重建整个应用。

### 4. 评分改动独立处理，避免给候选定做尺子

`note_lcs` 的偶然重合与合法使用备注事实确有方法风险，但不要直接换另一个随意阈值、短句一律放行或写死题目答案白名单。至少同时保护：

1. 合法使用可传达事实；
2. 短句偶合不误伤；
3. 私有情绪换词泄漏仍被识别；
4. 没有照搬字面却把未发草稿当成已约仍失败。

字符相似度适合作为复核提示，不能独立证明语义泄漏。将程序格式、事实语义、私有信息边界和表达多样性分开记账。评分版本更新后先对全部已有答卷离线重评，两臂统一使用同一把尺子，不需为此重烧 API。

### 5. 成本方向还未被新候选覆盖

原始记录中输入占总 token 约96.3%。当前每请求平均 system 8,295字符、user 745字符；这是字符统计，不能当作分段token精确归因。

下一轮应先按 system/知识/recent/ongoing/聊天/输出分别做离线体积审计，发现重复和常驻开销。v2 是召回修复候选，不是已验证的降本或架构重构成果。新增注入的体积、无关条目数、检索本地耗时都要随质量并列报告。
